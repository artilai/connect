Rules:

- Keep the codebase clean, readable and well defined. Make the smallest robust change that solves the task: write the least code that handles its real cases. Keep it extensible through its shape, so the next case of the same kind lands as an addition beside the existing ones rather than a rewrite. Reach for abstractions that name a real concept; leave out options and extension points nothing uses yet.
- Treat the existing design as a starting point, not a constraint: challenge weak patterns and fix them where the task touches. When the right fix is bigger than the task, propose it instead of working around the design.
- Solve each recurring problem one way. Before writing a feature folder, route, repository, command or channel, read its closest sibling and mirror its shape: `apps/server/src/messages` for a feature with routes, `apps/server/src/agents/repository.ts` for a repository, `apps/server/src/command/agents.ts` for a command, `packages/telegram-channel` for a channel with a provider and `packages/url-channel` for one the server carries itself.
- Name things plainly, the way Artil Cloud does: a repository method says what it does and by what, like `findById`, `findByHash`, `listByAgent`, `hasReceivedFrom` or `markSent`; a function that turns one shape into another is `toX`; a variable is the noun it holds, like `savedConfig` or `selectedAgentId`, not a participle like `held` or `chosen`.
- Write every change to pass a strict review by agents and humans: one concern per PR, in a diff a reviewer can follow without asking. Before handing it off, review your own diff that strictly and fix what you find.
- An `agent` is what Artil Cloud calls an identity in code; this server says agent everywhere.
- The `artil` CLI and its plugins are written against Artil Cloud's API, and installed CLIs lag behind. Keep each route the CLI calls at the cloud's path and shape: `bun run api:check` compares `docs/openapi.json` with the cloud's. Grow the API by adding endpoints, optional request fields, and new response fields, values and error codes; clients skip what they do not know.
- What only Artil Cloud does answers with `onlyInCloud` from `apps/server/src/cloud.ts`, so the CLI's command says where to go. A read the CLI makes while showing its status answers with nothing instead.
- Every channel implements the one `Channel` interface in `packages/channels/src/contract.ts`, in a package of its own named `<name>-channel` whose main export is its `ChannelDefinition`, named `channel`, and the server reaches channels only through it. A channel names itself and whom it sends to, so nothing in the server describes a channel for it. `packages/channels` holds types alone and names no channel: a channel's kind and what only it takes with a message (the `Data` of `Channel<Kind, Data>`) live in its package, and the server takes any kind: only the requests of the API, which the artil CLI knows from Artil Cloud, name the kinds in `apps/server/src/channels/kinds.ts`. Commands and the setup go by a channel's kind, name and descriptions, so a new channel needs none of its own. The config's `channels` list loads them, through `apps/server/src/channels/load.ts`, which names the built-in ones. Grow the interface by adding optional fields and new events, so every channel keeps working.
- A channel with a provider turns what the provider sends into `ChannelEvent`s and chooses how they come: the server runs `start` for each connected address, where the channel asks its provider for messages or points the provider at the server, and passes what the provider posts to `/api/channels/<kind>` to `handleWebhook`. A channel that only takes webhooks cannot work on a computer nothing can reach, so give it a way to ask as well. A channel the server carries itself, like the Message URL, hands each message to a host the server gives it.
- A channel carries messages and checks their shape; the server decides the rest. Who wakes an agent is `apps/server/src/access/admission.ts`, for every channel alike, and limits, listening and storage are the server's services.
- The server has no accounts: whoever runs it manages it with `artil-server`. Each client signs in as one agent, through the sign-in page or with a token from `artil-server agent token`, and the server keeps only hashes of tokens.
- Read the environment only in `apps/server/src/main.ts` and in scripts, and pass values in as arguments.
- Write standalone functions as `function` declarations. A declaration loses narrowing from guards above it, so copy the narrowed value into a `const` after the guard.
- Use the newest ES and TypeScript features over older idioms, e.g. `Object.groupBy`, `Map.groupBy`, iterator helpers, `Promise.withResolvers`, `using` and `satisfies`.
- Name object parameter types: `type <Component>Props` for components, `type <function>Options` for other functions. `bun run format` writes them.
- Every file in `apps/server/migrations` comes from Drizzle Kit: edit `apps/server/src/db/schema.ts` and run `bun run db:generate --name <snake_case_summary>`. Merged migrations are immutable, so fix one with a new migration. `bun run db:check` fails when the schema and migrations disagree.
- Tests build the whole server with `createTestServer` from `apps/server/src/testing.ts` and talk to it over HTTP, as clients do. Fake only what lies outside the server, like Telegram and the bucket. A rule that is a pure function, like admission, and a channel package are tested on their own.
- When a change alters what users see, update every text that describes it in the same PR: the READMEs, the command's help and what it prints.
- Each app and package has a `README.md`: `# <package name>`, one or two sentences on what it owns, then `## Usage` with its entry points, plus `## Development` and `## Deployment` where it has them. When code needs explaining, explain it in a short comment in plain words beside that code.
- A release ships only after the version in `apps/server/package.json` goes up.
- Title commits and PRs `type(scope): summary`, like `fix(server): keep the stream open behind Funnel`. Types: `feat`, `fix`, `perf`, `refactor`, `docs`, `chore`. Add a scope when the change stays in one app or package, or in `ci`. The summary is a lowercase phrase naming the outcome.
