Rules:

- Keep the codebase clean, readable and well defined. Make the smallest robust change that solves the task: write the least code that handles its real cases. Keep it extensible through its shape, so the next case of the same kind lands as an addition beside the existing ones rather than a rewrite. Reach for abstractions that name a real concept and make the code clearer; leave out options and extension points nothing uses yet.
- Treat the existing design as a starting point, not a constraint: challenge weak patterns and decisions, and fix them where the task touches. When the right fix is an architecture change bigger than the task, propose it instead of working around the design.
- Solve each recurring problem one way. Before writing a feature folder, route, repository, command or channel, read its closest sibling and mirror its shape. The reference shapes are `apps/server/src/domains/messages` for a domain and `packages/telegram-channel` for a channel. A domain's `service.ts` holds every rule, and its routes, tools and commands only read input, call the service and present the result, so the HTTP API, MCP and the CLI act alike.
- Name things plainly: a repository method says what it does and by what, like `findById` or `listByAccount`; a function that turns one shape into another is `toX`; a variable is the noun it holds, like `savedConfig`.
- Write every change to pass a strict review by agents and humans: one concern per PR, in a diff a reviewer can follow without asking. Before handing it off, review your own diff that strictly and fix what you find.
- The `artil` CLI and its plugins are written against Artil Cloud's API, and installed CLIs lag behind. Keep every route the CLI calls at the cloud's path and shape, and grow the API only by adding: endpoints, optional request fields, and new response fields, values and error codes. `bun run api:check` compares the API with the cloud's. What only Artil Cloud does answers with `onlyInCloud` from `apps/server/src/platform/cloud.ts`, so the CLI says where to go.
- Every channel extends `Channel` from `packages/channels` in a package of its own, which keeps its rules, texts and limits. A release that breaks channels built for the last one raises `contractVersion` in the contract by one, and the pull requests before it leave it as it is; the server loads only channels of its own version. The server names no channel but its own Message URL: `apps/server/src/main.ts` brings the built-in ones, the config loads the rest, and `apps/server/src/domains/access/admission.ts` decides who wakes an agent, for every channel alike. A channel that only takes webhooks cannot work on a computer nothing can reach, so give it a way to ask its provider as well.
- Nobody signs up to the server: whoever runs it manages it with `artil-connect`, and each client signs in as one account with a token, which the server keeps only as a hash.
- An account is what the server holds for one agent, the client that signs in as it: the code and every text call it an account, and agent means the client. The API and MCP keep Artil Cloud's names where its shape has them, like the `/agents` paths and `kind: "agent"`.
- Standalone functions are `function` declarations, which lose narrowing from guards above them: copy the narrowed value into a `const` after the guard.
- Use the newest ES and TypeScript features over older idioms, e.g. `Object.groupBy`, iterator helpers, `Set` methods, `Promise.withResolvers`, `using` and `satisfies`.
- Every file in `apps/server/migrations` comes from Drizzle Kit: edit `apps/server/src/platform/db/schema.ts` and run `bun run db:generate --name <snake_case_summary>`. Merged migrations are immutable, so fix one with a new migration.
- Tests build the whole server with `createTestServer` from `apps/server/src/app/testing.ts` and talk to it over HTTP, as clients do; they fake only what lies outside the server, like Telegram and the bucket. A pure rule, like admission, and a channel package are tested on their own.
- When a change alters what users see, update every text that describes it in the same PR: the READMEs, the command's help and what it prints.
- Each app and package has a `README.md` shaped like the others', and the root `README.md` says only what the server is and how to run it. When code needs explaining, explain it in a short comment in plain words beside that code.
- A release ships only after the version in `apps/server/package.json` goes up.
- Title commits and PRs `type(scope): summary`, like `fix(server): keep the stream open behind Funnel`. Types: `feat`, `fix`, `perf`, `refactor`, `docs`, `chore`. Add a scope when the change stays in one app or package, or in `ci`. The summary is a lowercase phrase naming the outcome.
