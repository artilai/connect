Rules:

- Keep the codebase clean, readable and well defined. Make the smallest robust change that solves the task: write the least code that handles its real cases. Keep it extensible through its shape, so the next case of the same kind lands as an addition beside the existing ones rather than a rewrite. Reach for abstractions that name a real concept and make the code clearer; leave out options and extension points nothing uses yet.
- Treat the existing design as a starting point, not a constraint: challenge weak patterns and decisions, and fix them where the task touches. When the right fix is an architecture change bigger than the task, propose it instead of working around the design.
- Solve each recurring problem one way. Before writing a feature folder, route, repository, command or channel, read its closest sibling and mirror its shape. The reference shapes are `apps/server/src/domains/messages` for a domain and `packages/telegram-channel` for a channel; `apps/server/AGENTS.md` holds the server's layout.
- Name things plainly, the way Artil Cloud does: a repository method says what it does and by what, like `findById` or `listByAgent`; a function that turns one shape into another is `toX`; a variable is the noun it holds, like `savedConfig`, not a participle like `chosen`.
- Write every change to pass a strict review by agents and humans: one concern per PR, in a diff a reviewer can follow without asking. Before handing it off, review your own diff that strictly and fix what you find.
- An `agent` here is what Artil Cloud calls an identity in code.
- The `artil` CLI and its plugins are written against Artil Cloud's API, and installed CLIs lag behind. Keep every route the CLI calls at the cloud's path and shape, and grow the API only by adding: endpoints, optional request fields, and new response fields, values and error codes. `bun run api:check` compares the API with the cloud's. What only Artil Cloud does answers with `onlyInCloud` from `apps/server/src/platform/cloud.ts`, so the CLI says where to go.
- Every channel extends `Channel` from `packages/channels`, in a package of its own; the Message URL is the server's own channel, in `apps/server/src/domains/url`. A channel names itself, carries messages and checks their shape, and keeps its rules, texts and limits. The server reaches a channel only through the class and names no other: `apps/server/src/main.ts` brings the built-in ones and the config loads the rest. Who wakes an agent is `apps/server/src/domains/access/admission.ts`, for every channel alike, and listening and storage are the server's. A channel with a provider keeps messages coming in `start` and takes what the provider posts to `/api/channels/<kind>` in `handleWebhook`; one that only takes webhooks cannot work on a computer nothing can reach, so give it a way to ask as well.
- The server has no accounts: whoever runs it manages it with `artil-server`, and each client signs in as one agent with a token, which the server keeps only as a hash.
- Write standalone functions as `function` declarations. A declaration loses narrowing from guards above it, so copy the narrowed value into a `const` after the guard.
- Use the newest ES and TypeScript features over older idioms, e.g. `Object.groupBy`, iterator helpers, `Set` methods, `Promise.withResolvers`, `using` and `satisfies`.
- Name object parameter types: `type <Component>Props` for components, `type <function>Options` for other functions. `bun run format` writes them.
- Every file in `apps/server/migrations` comes from Drizzle Kit: edit `apps/server/src/platform/db/schema.ts` and run `bun run db:generate --name <snake_case_summary>`. Merged migrations are immutable, so fix one with a new migration. `bun run db:check` fails when the schema and migrations disagree.
- Tests build the whole server with `createTestServer` from `apps/server/src/app/testing.ts` and talk to it over HTTP, as clients do; they fake only what lies outside the server, like Telegram and the bucket. A pure rule, like admission, and a channel package are tested on their own.
- When a change alters what users see, update every text that describes it in the same PR: the READMEs, the command's help and what it prints.
- Each app and package has a `README.md`: `# <package name>`, one or two sentences on what it owns, then `## Usage` with its entry points, plus `## Development` and `## Deployment` where it has them. The root `README.md` says only what the server is and how to run it. When code needs explaining, explain it in a short comment in plain words beside that code.
- A release ships only after the version in `apps/server/package.json` goes up.
- Title commits and PRs `type(scope): summary`, like `fix(server): keep the stream open behind Funnel`. Types: `feat`, `fix`, `perf`, `refactor`, `docs`, `chore`. Add a scope when the change stays in one app or package, or in `ci`. The summary is a lowercase phrase naming the outcome.
